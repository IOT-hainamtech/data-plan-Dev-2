## Executive result

The current application source passes the complete enabled backend regression, both ESP32
cross-builds, firmware payload/provisioning contracts, fresh migrations and idempotent migration
rerun. No application business-logic change was required by this audit. Documentation was grouped
by purpose and portable VS Code C/C++ configuration was added so IntelliSense consumes the real
PlatformIO compilation database.

One optional host-native C++ test remains environment-blocked because `gcc` and `g++` are not on
the Windows host `PATH`. This is not an ESP32 compiler failure: both declared ESP32 environments
build successfully with the installed Xtensa/ESP-IDF toolchain. Physical ESP32/SHT31/MC-38
acceptance remains hardware-blocked.

## Firmware architecture and build

Firmware is a PlatformIO project using the ESP-IDF framework and `esp32dev` target. The root and
component CMake files are ESP-IDF inputs used by PlatformIO; this is a combined
PlatformIO + ESP-IDF setup, not two conflicting build systems. Both device environments use
C++17 and the same contract implementation:

| Target | Environment | Result | Memory |
| --- | --- | --- | --- |
| S1 ESP32 + SHT31 | `sht31` | PASS | RAM 10.6%, Flash 60.9% |
| S6 ESP32 + MC-38 | `reed_door` | PASS | RAM 10.6%, Flash 60.9% |
| Firmware Python contracts | `firmware/tests` | 9 PASS, 0 FAIL, 0 SKIP | N/A |
| Native C++ contract | `native` | ENVIRONMENT_BLOCKED | Host lacks `gcc`/`g++` |

The builds confirm that `<cstdint>`, `<string>`, local headers, `nvs.h`, `nvs_flash.h` and other
ESP-IDF dependencies resolve through the actual toolchain. The editor configuration uses
`${workspaceFolder}` and contains no machine-specific compiler path. After opening the repository,
run/build `sht31` once if `.pio` was removed, then use **C/C++: Reset IntelliSense Database** and
confirm the VS Code Problems panel. This audit cannot directly inspect the GUI Problems panel.

Firmware payload checks confirm the established MQTT topic and JSON contracts for S1 telemetry,
sensor error reports, S6 door events/status, timestamps, boot/sequence/event identity and QoS 1.
No protocol field or topic was changed.

## Remaining warnings and blockers

- The optional native PlatformIO test requires a host C/C++ compiler. Install a supported native
  toolchain and rerun `pio test -e native`; do not confuse this with the passing ESP32 builds.
- MQTT `unknown ca` and abrupt TLS EOF messages occurred during the deliberate negative TLS and
  disconnect tests. They are expected security-test evidence, not a broker restart loop.
- Temporary HTTP 422 delivery warnings were produced while regression tests intentionally created
  invalid/isolated events. Test cleanup completed; both durable queues ended with zero pending and
  zero failed rows.
- Physical sensor wiring, flashing, Wi-Fi/NTP/TLS behavior, SHT31 measurements, MC-38 polarity and
  power-loss/LWT behavior remain `HARDWARE_BLOCKED`.
- Dev 1 must still correct and resynchronize the swapped `NW-TEST-TH`/`NW-TEST-DOOR` profiles and
  invalid/disabled `NW-TEST-R01`/`NW-TEST-R02` rules at higher versions.
- Real Bridge acceptance still requires the Dev 1 token, confirmed health behavior and UI evidence;
  Snapshot must remain on Mock until its real contract is confirmed.
